# <center> Unibuy DEX 协议 v0.2 </center>

<center> Derik Lu,  ldru0519@gmail.com, 2026年5月28日</center>

## 0. 摘要
Unibuy 是一个基于常量乘积公式实现的类订单簿交易协议。中心化交易所订单簿的价格是用户设定的单点价格，Unibuy 订单簿的价格是常量乘积曲线上用户指定的一个价格区间。

Unibuy 协议为一对交易 Token 设置两个互为镜像关系的单向交易资金池，具有跟 Uniswap 的双向交易资金池相似的交易体验。单向交易对的效果是两个镜像交易对之间总会自动保持一个小的价差，该价差可以有效阻止目前 DEX 交易中大量存在的三明治攻击。

用户的订单基本分成两类：挂单和吃单。挂单是在指定的价格范围内卖出指定数量的 $\small token_0$，要求价格范围的低端价格镜像转换后，必须低于关联镜像交易对的当前价格，确保挂单交易不会立即成交。吃单是在不超过指定最高限价的前提下买入指定数量的 $\small token_0$ 或卖出指定数量的 $\small token_1$，要求最高限价必须高于交易对的当前价格，吃单交易总是立即成交。

单向交易对总是卖出 $\small token_0$，买入 $\small token_1$，关联镜像交易对中 $\small token_0$ 和 $\small token_1$ 的定义则正好相反。从挂单用户的角度看，挂单始终是卖出 $\small token_0$、买入 $\small token_1$；从吃单用户的角度看，则是卖出 $\small token_1$、买入 $\small token_0$。挂单与吃单互为交易对手，同一 Token 的买入和卖出由两个关联的镜像交易对共同完成。

用户的吃单交易总是驱动 $\small token_0$ 的价格沿常量乘积曲线单向上升，而用户的挂单交易则可能压低当前交易对的价格。Unibuy 协议中的挂单在全部或部分成交后，即使价格随后反转，也不会像 Uniswap 协议中的流动性那样被动买回已卖出的 $\small token_0$，从而避免 Uniswap 做市商面临的无偿损失问题。

Unibuy 协议设计了区间流动性再平衡机制以及挂单前向补偿机制，可以解决挂单交易中可能隐含存在的内部交易套利问题，实现不同价格区间的用户挂单流动性的聚合。

Unibuy 协议的流动性由用户的挂单提供，没有 Uniswap 协议中的自动做市商的角色，用户的交易费用全部成为 Unibuy 协议的协议收入。

## 1. 导言

Uniswap$^{[1,2,3,4]}$ 协议持续升级，从 v1/v2 到 v3/v4，不断改进和优化常量乘积自动做市商 CPAMM 机制的具体实现方式，提升做市资金的利用效率，成为 Defi 领域公认的 DEX 龙头应用，其核心机制被很多 Web3 项目效仿。但是，Uniswap 类型的 DEX 也面临不少问题。

### 1.1 协议收入问题

Uniswap 协议中，需要流动性提供商提供用于用户交易的流动性，作为回报，流动性提供商获得绝大部分交易用户所支付的交易手续费，DEX 项目方只能获得交易手续费的很小一部分。Uniswap 为分割交易手续费设置了开关，需要通过投票才能打开开关，甚至导致 Uniswap 无法从用户的交易收费中获益。 

### 1.2 无偿损失问题

常量乘积自动做市商机制虽然解决了 Token 交易中的自动定价问题，但也不可避免地带来了难以解决的无偿损失问题$^{[5]}$。专业做市商可以通过持续监控交易对状态，并根据价格变化及时调整流动性分布，在一定程度上缓解无偿损失。普通 Web3 用户通常缺乏相应工具和能力，如果长期提供流动性而不及时调整，有限的做市收益往往无法覆盖所承受的无偿损失。这会显著打击普通用户参与做市的积极性，并影响 DEX 流动性的来源。

### 1.3 三明治攻击问题

Uniswap 交易对是双向交易对，Token 的卖出价格同时也是其买入价格。用户交易后，Token 价格会沿着常量乘积曲线滑动，因此很容易遭受三明治攻击。攻击者可以在用户的大额交易之前抢先发起同方向的买入或卖出交易，使交易对的 Token 价格朝着不利于用户的方向移动；待用户交易完成后，再发起一笔反向交易完成套利。从链上交易信息中可以观察到大量这样的攻击交易。针对三明治攻击，虽然已经提出不少解决方案$^{[6,7]}$，但仍然难以普遍适用。

Unibuy 协议从设计机制上，可以原生解决上述三大问题。

### 1.4 Unibuy 协议的解决方案

Unibuy 协议采用类似于中心化交易所的订单簿机制，不再存在流动性做市商的角色，用户的交易手续费全部归属于 Unibuy 协议运行方，从而可以天然解决交易手续费的分配问题。

与中心化交易所的订单簿类似，Unibuy 协议的流动性由等待成交的用户挂单提供。用户的吃单交易成交后，交易对收到的 $\small token_1$ 不会再投入交易，而是即刻离场，不会像常量乘积做市协议一样，做市资金反复被动地买入或卖出。由于不存在做市商的角色，自然也就不存在做市资产因价格大幅变化遭受无偿损失的问题。

Unibuy 协议的订单簿交易机制设计中，交易对的交易是单向的，为实现 Token 的双向买卖交易，需要两个相互关联的互为镜像的单向交易对来实现。这种单向交易对的设计只是一种内部技术实现方式，不会影响交易用户的交易体验。但单向交易对的技术实现带来一个效果，即这两个镜像交易对中，同一 Token 的买入和卖出价格会天然地保持一个价差，这个天然存在的价差能够有效抵御三明治攻击。攻击者虽然可以抢跑完成交易，但因为抢跑交易无法影响镜像交易对的 Token 价格，也就无法通过反向交易完成套利，使得抢跑没有意义。

### 1.5 与 CEX 订单簿的区别

Unibuy 协议的订单簿和中心化交易所的订单簿也是有区别的。

在中心化交易所，用户发出买入或卖出订单时，如果该订单能够与订单簿中的既有订单匹配，就会立即成交，这类订单称为吃单。如果不能立即成交，订单就会被加入订单簿，并在交易界面中显示，等待后续订单来匹配。订单中的价格是单点价格，订单簿中的全部订单共同构成价格轴上的一组离散点。

Unibuy 协议中，订单的价格不是一个单点价格，而是一个价格范围，在这个价格范围内，订单中给定数量的 Token 会按照常量乘积曲线自动成交。Unibuy 协议会根据用户给出的参数，自动执行吃单和/或挂单交易，如果订单只能部分成交，按照用户的要求，未成交部分可以转为挂单等待后续吃单，也可以部分成交后直接结束交易。所有价格区间的区间流动性叠加在一起，成为吃单交易的流动性。

Unibuy 协议不使用中心化交易所采用的按照价格及下单顺序进行订单匹配的交易规则。Unibuy 协议将所有挂单资产聚合在一起，为吃单交易提供流动性，吃单交易按照常量乘积曲线定义的规则，确定买入/卖出 Token 的数量。

Unibuy 协议的挂单在区块链上是公开可见的，是真实的用户订单，可以避免中心化交易所的虚假订单、冰山订单等误导交易用户的问题。由于区块时间的不连续性，以及交易的竞争性，在区块链上进行虚假挂单，会面临很大风险，没有利用价值。

中心化交易所通常会为挂单提供低于吃单的交易费率，以鼓励用户提供流动性。Unibuy 协议中的挂单无论是否成交，始终都是免费的。

曾经有一些项目尝试实现订单簿功能的 DEX，如 EtherDelta$^{[8]}$、Serum$^{[9]}$ 等，但这些项目只是将传统 CEX 订单簿的功能简单复制到区块链上，缺少技术上的创新，没有结合和利用区块链的特点，由于各种原因，也都不太成功。在链上实现订单簿功能应该需要在技术层面做一些突破和创新。

### 1.6 Unibuy 协议

Unibuy 是一个提供订单簿功能的去中心化交易协议。该协议结合了常量乘积自动做市商的机制，以及中心化交易所订单簿的功能特点，既能够聚合用户的挂单资产为吃单交易提供流动性，又不需要在链上实现复杂的订单匹配机制，希望能够探索出一个实现链上订单簿功能 DEX 的可行之路。

Unibuy 协议为一对交易 Token 设置两个互为镜像的交易对，每个交易对提供单一 Token 的卖出服务，两个单向交易对关联在一起，实现 Token 交易对的买入/卖出服务。

利用两个关联的单向交易对实现 DEX 协议的想法，FeSwap$^{[10]}$ 曾经进行过尝试。Feswap 利用这一设计实现了一个完全免费但又有做市收益的 DEX。该项目由于缺少推广，用户不多，但也一直在持续运行，积累了不少链上交易。Unibuy 协议的关联单向交易对的设计，表面类似，但却是一个完全不同的链上订单簿功能的技术实现。

为了聚合不同用户、不同价格范围、不同批次的挂单流动性，Unibuy 设计了流动性再平衡机制以及挂单前向补偿机制，使挂单流动性能够聚合在一起，为吃单交易提供流动性，同时避免实现类似中心化交易所那样复杂的订单匹配与清算机制。下面将详细介绍 Unibuy 协议的技术方案。

## 2. Unibuy 交易协议

### 2.1 区间流动性基础

在 Uniswap v3/v4 中，为了提高做市资金的利用效率，做市商可以指定做市的价格范围，从而避免资金分布于永远不会触及的价格区间，造成资金浪费。Uniswap 引入 $\small tick$ 概念，tick 是离散的不连续的整数，可以对应到交易对的 Token 价格，利用 $\small tick$ 可以将做市资金分割成多个不同的价格区间，使得同一价格范围的做市资金能够相互聚合，统一参与 Token 买卖交易。而当交易对的价格发生变化，跨越价格区间时，再对交易对的流动性参数进行调整，使得交易对在每个价格区间，都服从常量乘积公式，只是流动性参数不同。

通过 $\small tick$ 限定做市资金的价格范围，做市商提供的资金只要能够覆盖指定的价格范围即可，相对于 Uniswap v1/v2 中 $\small (0, \infty)$ 的做市价格范围，同等做市资金规模可以提供更多的交易流动性，这就是 Uniswap 虚拟流动性的概念。

<center> 图1. 区间流动性 </center>

图1 是一个价格区间，也即 $\small tick$ 区间的示意图，其价格范围为 $\small (P_a, P_b)$，虚拟流动性常量为 $\small L$，交易对两个 Token 的虚拟数量为 $\small x, y$，恒定乘积公式表示为：

$$ 
  \small x * y = L^2 \tag{2.1.1} 
$$

形式上，该公式与 Uniswap v1/v2 中的恒定乘积公式的表示形式是一样，但含义是有区别的。Uniswap v1/v2 中，恒定乘积公式中的 $\small x,y$ 是两种资产的真实数量，常数 $\small L$ 在整个价格空间内保持不变。而在 Uniswap v3/v4 以及 Unibuy 协议中，$\small x,y$ 是两种资产的虚拟数量，常数 $\small L$ 只是在 $\small tick$ 区间内部保持不变，而不同 $\small tick$ 区间的 $\small L$ 往往是不一样的。

Unibuy 协议内部，真正具有实际意义的是，价格区间虚拟资产数量的差，即 $\small \Delta x, \Delta y$，其满足如下公式：

$$ 
  \small \Delta x = (\frac{1}{\sqrt{P_a}}- \frac{1}{\sqrt{P_b}}) * L \tag{2.1.2} 
$$

$$ 
  \small \Delta y = (\sqrt{P_b}- \sqrt{P_a}) * L \tag{2.1.3} 
$$

$$ 
  \small \frac{\Delta y}{\Delta x} = \sqrt{P_a * P_b }   \tag{2.1.4} 
$$

在 Unibuy 协议中，当用户挂单在 $\small (P_a, P_b)$ 价格范围出售数量为 $\small \Delta x$ 的一种资产时，利用公式 $\small (2.1.2)$，可以计算出与挂单资产相对应的该价格区间的虚拟流动性 $\small L$，协议内部会记录用户加入的虚拟流动性 $\small L$。同一价格区间不同用户的虚拟流动性的简单叠加，就可以实现虚拟流动性的聚合。

当用户吃单时，由于虚拟流动性常量 $\small L$ 已知，根据希望卖出的资产数量 $\small \Delta y$ 或者希望买入的资产数量 $\small \Delta x$，利用公式 $\small (2.1.3)$ 或 $\small (2.1.2)$ 就可以计算出交易对的价格变化，进而得到对应的 $\small \Delta x$ 或 $\small \Delta y$。

公式 $\small (2.1.4)$ 的含义是 $\small \Delta x$ 的一种资产与 $\small \Delta y$ 的另一种资产在 $\small (P_a, P_b)$ 价格范围内互换时，其平均价格为 $\small \sqrt{P_a * P_b}$。

### 2.2 单边流动性

Unibuy 协议继承了 Uniswap v3/v4 虚拟流动性的设计，所有的流动性分割成不同的 $\small tick$ 区间，也即价格区间，在同一个 $\small tick$ 区间内，虚拟流动性常量 $\small L$ 保持不变。交易过程中，当交易对的价格发生变化，并且跨越 $\small tick$ 边界时，流动性常量 $\small L$ 会根据跨越 $\small tick$ 记录的信息，进行相应调整。

但是，Unibuy 协议与 Uniswap 协议也存在明显差异。Uniswap 在 $\small tick$ 区间内的交易是双向的，而 Unibuy 协议在 $\small tick$ 区间内的交易是单向的。这一差异决定了 Unibuy 协议的流动性只存在于交易对当前价格上方，而 Uniswap v3 的流动性则可以分布于整个价格空间。下图展示了 Unibuy 协议中的流动性分布。

Uniswap 协议中，同一个交易对支持 $\small token_0$ 和 $\small token_1$ 的相互交换。流动性提供商提供可供交易的流动性，交易用户支付约 $\small 0.3\%$ 的交易手续费，流动性提供商赚取该手续费，Uniswap 仅收取其中的一小部分，或者在某些情况下不收取手续费。

Unibuy 协议中，不存在流动性提供商这一角色，全部交易流动性均来自用户挂单。挂单只需要提供一种 Token 资产，在协议中定义为 $\small token_0$；吃单则总是用 $\small token_1$ 去换取交易对中的 $\small token_0$。用户买入或卖出 $\small token_0/token_1$ 的交易功能，实际上是通过两个相互关联、互为镜像的单向交易对实现的。Uniswap 协议中的增加流动性、撤回流动性和兑换交易，分别对应 Unibuy 协议中的挂单、关闭挂单和吃单。从用户角度看，Unibuy 协议提供的体验更接近中心化交易所。Unibuy 协议中，吃单需要支付一定的交易手续费，而挂单无论是否成交都不收取手续费；吃单手续费全部归属于 Unibuy 协议。

### 2.3 单向交易对

DEX 协议总是需要提供双向交易功能。Unibuy 协议的双向交易能力由两个关联在一起、互为镜像的单向交易对实现。在两个关联交易对中，$\small token_0$ 和 $\small token_1$ 的定义正好相反。以 Token A/B 为例：如果在一个交易对中 Token A 是 $\small token_0$、Token B 是 $\small token_1$，那么在其镜像交易对中，Token A 就是 $\small token_1$、Token B 则是 $\small token_0$。由于这种对称关系，两个镜像交易对的功能逻辑完全一致，即用户始终以 $\small token_1$ 换取挂单用户卖出的 $\small token_0$。这种两个相互关联的单向交易对的方案只是内部技术实现，挂单用户和吃单用户无需关注这一细节，也不会影响实际交易体验。

当用户挂单时，需要设定卖出 $\small token_0$ 的价格范围及数量，所有的用户挂单聚合在一起，形成交易对的流动性。用户吃单时，交易对手是聚合在一起的挂单的流动性。由于吃单交易总是用 $\small token_1$ 交换 $\small token_0$，所以吃单交易总是造成 $\small token_0$ 的价格单向上涨。

用户挂单时指定的价格范围，可以高于或低于交易对的当前价格，但低端价格镜像转换后不得高于镜像交易对中的当前价格，(镜像交易对的价格是本交易对价格的倒数)。原因是如果高于关联交易对的当前价格，高于价格的部分是可以在关联交易对中立即成交的。Unibuy 协议可以根据用户给出的价格范围，以及交易对的当前状态，将用户订单按照挂单或吃单处理，如果需要，可以先按照吃单部分成交，未成交部分按照挂单处理。

如果用户挂单的低端价格低于交易对的当前价格，交易成功后，低端价格会成为交易对的当前价格，该价格会成为后续吃单交易的起点价格。但如果挂单的低端价格高于当前价格，则不会改变交易对的当前价格。

## 3. Unibuy 内部机制

Unibuy 协议单向交易机制的设计虽然可以解决三明治攻击、协议收入等问题，但也为聚合不同挂单的流动性，以及正确计算用户挂单的成交收入也带来不小的复杂性，Unibuy 协议设计了再平衡机制、内部交易补偿机制等机制来处理这种复杂性。

### 3.1 流动性再平衡机制

用户挂单时，如果指定价格范围 $\small (P_l, P_u)$ 的低端价格 $\small P_l$ 低于交易对的当前价格 $\small P_0$ ，会触发流动性再平衡机制。原因是在交易对的当前价格区间，流动性可能是部分成交的。而用户挂单的价格区间跟当前的价格区间可能有重叠，这两类流动性是没法直接聚合在一起的。需要将部分成交的流动性再平衡到需要的价格区间，才能进行流动性的叠加。另外，这类挂单交易挂单成功后，$\small P_l$ 会成为交易对的最新价格，这也需要将当前价格区间的流动性进行再平衡，便于聚合后面的流动性。

新加入的流动性，相对于当前的价格区间，可能存在图 3 所示的 10 种情况，其中 1/2/5 由于 $\small P_l$ 高于当前价格 $\small P_0$，不需要进行流动性再平衡，其他几种情况都需要进行流动性再平衡。4/7/10 需要再平衡到当前流动性区间的低端价格 $\small P_a$ ，8/9 需要再平衡到新加流动性的高端价格 $\small P_u$ ，3/6 需要再平衡到新加流动性的低端价格 $\small P_l$。

再平衡后的价格区间的高端价格 $\small P_b$ 保持不变，低端价格 $\small P_r$ 由下式决定:

$$ 
  P_r = \left\{ 
  \begin{aligned} 
  \ \ &P_u    &(tick_u \geqslant tick_a) \ \& \ (tick_u \leqslant tick_0) \\
  \ \ &P_l    &(tick_l \geqslant tick_a) \ \& \ (tick_l \leqslant tick_0) \\
  \ \ &P_a    &others \\
  \end{aligned} 
  \right. \tag{3.1.1} 
$$ 

其中 $\small tick_a、tick_b、tick_0、tick_u、tick_l$ 分别是为与价格 $\small P_a, P_b, P_0, P_u, P_l$ 对应的 $\small tick$，该公式仅适用于  $\small tick_l \leqslant tick_0$ 的情况，$\small tick_l \gt tick_0$ 时不需要再平衡。上式中，$\small P_r$ 的赋值顺序为 $\small P_u \gt P_l \gt P_a$，即如果满足 $\small P_u$ 条件，则 $\small P_r = P_u$，否则如果满足 $\small P_l$ 条件，则 $\small P_r = P_l$，否则 $\small P_r = P_a$。

当 $\small P_r = P_u$ 或 $\small P_l$，需要对当前流动性区间进行拆分处理，将 $\small (P_a, P_r)$ 之间的流动性按照已经完全成交处理，处理顺序是先进行流动性区间进行拆分，再进行流动性再平衡。

设当前交易对的价格为 $\small P_0$，再平衡后新的价格范围为 $\small (P_{r}, \ P_{b})$，当前流动性区间的流动性为 $\small L_1$。由于当前价格为 $\small P_{0}$ ，意味着当前流动性区间只在 $\small (P_{0}, P_{b})$ 之间还有流动性，$\small (P_a, P_0)$ 之间的流动已经成交卖出。再平衡的目的是让未成交的 $\small token_0$ 重新布满整个 $\small (P_{r}, P_{b})$ 价格空间，从而可以与新加入的流动性进行聚合。再平衡之后，由于当前流动性区间可供出售的 $\small token_0$ 数量不变，根据公式 $\small (2.1.2)$，新的虚拟流动性 $\small L_2$ 满足：

$$
  \begin{aligned} (\frac{1}{\sqrt{P_{r}}} - \frac{1}{\sqrt{P_{b}}}) * L_{2} = (\frac{1}{\sqrt{P_{0}}} - \frac{1}{\sqrt{P_{b}}}) * L_1 \end{aligned} \tag{3.1.2}
$$

$$
  \begin{aligned} L_{2} = \frac{\sqrt{P_{b}}-\sqrt{P_{0}}}{\sqrt{P_{0}}} * \frac{\sqrt{P_{r}}}{\sqrt{P_{b}}-\sqrt{P_{r}}} * L_1 \end{aligned} \tag{3.1.3}
$$

同时有：

$$
  \begin{aligned} L_{1} - L_{2} = \frac{\sqrt{P_{0}}-\sqrt{P_{r}}}{\sqrt{P_{0}}} * \frac{\sqrt{P_{b}}}{\sqrt{P_{b}}-\sqrt{P_{r}}} * L_1 \end{aligned} \tag{3.1.4}
$$

再平衡是将当前价格区间未成交的剩余流动性，重新分配到再平衡后的新的完整价格区间 $\small (P_r, P_b)$，与低端 $\small tick_r$ 对应的 $\small tickInfo$（参见4.2）结构中的 $\small LiquidityNet$ 会更新为 $\small L_{2}$，再平衡后净流动性减少的数量为 $\small L_1 - L_2$。

再平衡机制除了影响当前价格区间的流动性外，也会影响当前交易对的价格，再平衡后，新加入流动性的低端价格成为交易对的最新价格。没有进行再平衡的情况，交易对的价格维持不变。用户的吃单交易总是导致交易对的价格单向上涨，而用户的挂单可能会由于更低价格流动性的加入导致交易对价格的下跌。

由于再平衡机制的设计，用户的价格范围为 $\small (P_a, P_b)$ 的流动性并不能保证最终会按照 $\small \sqrt{P_a * P_b}$ 的平均价格卖出，经过多次再平衡后，实际 $\small token_0$ 卖出的平均价 $\small P_m$ 会满足 $\small P_a < P_m \leqslant \sqrt{P_a * P_b}$ 。这个设计可以让用户的流动性在用户指定的价格范围内以最快的速度成交，同时由于常量乘积定价曲线的约束，又可以尽量保证流动性有最好的成交价格。

## 3.2 内部交易补偿机制

当用户挂单时，新订单的流动性会跟已经存在的流动性聚合在一起，为吃单交易提供作为交易对手的流动性。而已经存在的流动性在其价格区间内可能已经部分成交，并且已经通过再平衡机制将剩余 $\small token_0$ 重新分布到其流动性空间的整个价格区间。而新加入的流动性，在该价格区间是完全未成交的流动性，与已经存在的流动性是内在价值不同的流动性。另一方面，由于常量乘积交易机制的限制，这两种流动性必须聚合在一起，参与吃单交易的统一处理。为解决这一问题，Unibuy 协议设计了内部交易补偿机制，在考虑先期挂单拥有价值优势的前提下，使得不同挂单不同交易状态的流动性能够获得内在一致的价值，既可以统一参于吃单交易处理，又可以在清算用户的订单时，正确计算各个订单的内含价值。

内部交易补偿机制只针对已部分成交的价格区间，完全没有成交的价格区间，或者已经完全成交的价格区间，不需要进行补偿机制处理。

假设在加入流动性前，流动性区间的总流动为性 $\small L_1$，已经部分成交，收到  $\small token_1$ 的数量设为 $\small R$。经过再平衡后，剩余的净流动性为 $\small L_2$。设新加入的流动性为 $\small L_d$，加入新的流动性后，该流动性区间的总流动性为 $\small L_1 + L_d$，总的净流动性为 $\small L_2 + L_d$，接收到的 $\small token_1$ 数量依然是 $\small R$，状态如下表所示:

$$ 
  \small \newcommand{\arraystretch}{1.8} \begin{array}  {| c ||  c | c | c |}
  \hline
  \text{区间流动性状态} &\text{总流动性}  &\text{净流动性}     &token_1\ \text{数量} \\
  \hline
  \text{加入新流动性前}  &{L_1}        &L_2          &R \\
  \hline
  \text{加入新流动性后}  &{L_1 + L_d}  &{L_2 + L_d}  &R \\
  \hline  
  \text{撤回新流动性后}  &{L_1}    &{\dfrac{L_1}{L_1 + L_d} * (L_2 + L_d)}  &{\dfrac{L_1}{L_1 + L_d}} * R \\[0.15cm]
  \hline  
 \end{array}
$$

由于用户的资产权益始终按照其占总流动性的比例计算，如果后发用户（下文记为用户 $\small 2$）在加入流动性后立即关闭订单，则该用户得到的 $\small token_1$ 数量 $\small R_x$ 为：

$$
  \begin{aligned} \small R_x = \frac{L_d}{L_1+ L_d} * R \end{aligned} \tag{3.2.1}
$$
 
 撤回的流动性为 $\small L_d * (L_2+ L_d) / (L_1+ L_d)$。相对于用户 $\small 2$ 初始加入的流动性 $\small L_d$，其减少的数量 $\small L_x$ 为：

$$
  \begin{aligned} \small L_x = \frac{L_d}{L_1 + L_d} * (L_1 - L_2) \end{aligned} \tag{3.2.2} 
$$
  
流动性的减少对应于 $\small token_0$ 的减少，这等价于用户 $\small 2$ 用一部分 $\small token_0$ 换取了数量为 $\small R_x$ 的 $\small token_1$，这是一种内部隐含的交换，不是显性的交易。与流动性 $\small L_x$ 相对应、被内部交换出去的 $\small token_0$ 数量记为 $\small S_x$（也就是用户 $\small 2$ 立即撤回流动性时减少的 $\small token_0$ 数量）：

$$
  \begin{aligned} \small S_x \ = \ &(\frac{1}{\sqrt{P_r}} - \frac{1}{\sqrt{P_b}}) * L_x \\[3mm]
  = \ &\frac{L_d}{L_1 + L_d} * (\frac{1}{\sqrt{P_r}} - \frac{1}{\sqrt{P_0}}) * L_1 \\
  \end{aligned} \tag{3.2.3} 
$$

成功关闭订单后，用户 $\small 2$ 相当于用价格范围为 $\small (P_r, P_b)$、数量为 $\small L_x$ 的流动性所对应的 $\small S_x$ 数量的 $\small token_0$，换取了数量为 $\small R_x$ 的 $\small token_1$。由于 $\small (L_1-L_2)$ 的 $\small token_0$ 流动性价值等价于数量为 $\small R$ 的 $\small token_1$，因此这一内部交换在价值上是合理的。不难验证，$ \small R_x = S_x * \sqrt{P_r * P_0}$，其中 $\small \sqrt{P_r * P_0}$ 是内部 $\small token_0$ 与 $\small token_1$ 互换的平均价格。

相应地，在订单被关闭后，该价格区间的流动性相对于新增订单加入之前的流动性 $\small L_2$ 增加了 $\small L_d * ( L_1 - L_2 ) / (L_1 + L_d)$，即 $\small L_x$；与此同时，$\small token_1$ 的数量变为 $\small R * L_1 / (L_1 + L_d)$，相对于最初的 $\small R$ 减少了 $\small R_x$。这等价于该流动性区间用数量为 $\small R_x$ 的 $\small token_1$ 换回了等值的 $\small token_0$ 流动性。

虽然该内部交换按照流动性再平衡时交易对的状态考虑，价值上是等价的，但是该交换对于先期加入流动性的用户来说，(后面统称用户 $\small 1$，代表一个或多个用户)，却是不合理的。原因是只要触发内部交换机制，用户 $\small 1$ 已成交的流动性的成交价格，一定会高于交易对的当前价格，或新加入流动性的低端价格。如果没有合理的机制对先加入流动性的用户 $\small 1$ 进行补偿，相当于后面的用户 $\small 2$ 用一定数量的 $\small token_0$ 以高于交易对的当前价格换成了 $\small token_1$，这实际上是用户 $\small 2$ 对先加入流动性用户的隐形套利，是不合理的。Unibuy 协议设计了内部交易补偿机制，让用户 $\small 2$ 对用户 $\small 1$ 按照规则进行合理的补偿。该补偿机制可以消除隐形套利的不合理性，并让用户 $\small 1$ 获得一定的先发优势。在中心化交易所，同等价格情况下，订单是按照用户的挂单先后顺序进行匹配的，先挂单用户有一定的先发优势。而 Unibuy 协议不处理用户订单的时间顺序，用户的先发优势是通过内部补偿机制体现的。

Unibuy 协议的补偿包含两个部分，一是内部交易补偿费，用 $C_a$ 表示 ；一是内部交易价差补偿费，用 $C_b/C_c$ 表示，下面分别介绍。

### 3.3 内部交易补偿费

Unibuy 协议规定，Unibuy 协议后期挂单的用户 $\small 2$，需要按照设置的内部交易补偿费率，以及内部交易金额，支付内部交易补偿费。内部交易补偿费以 $\small token_1$ 支付，设交易补偿费费率为 $\small r$ ，内部交易补偿费金额为：

$$ 
  \small \begin{aligned} C^{'}_{a} = r * \frac{L_{d}}{L_{1} + L_{d}} * R \end{aligned} \tag{3.3.1}
$$

由于内部交易补偿费是所有 $\small tickInfo$ 中记录的流动性都会按比例分配，包括用户 $\small 2$ 自己。为了确保用户 $\small 1$ 能够得到上面的补偿费，用户 $\small 2$ 支付的名义补偿费为：

$$ 
  \small \begin{aligned} C_{a} = r * \frac{L_{d}}{L_{1}} * R \end{aligned} \tag{3.3.2}
$$

易于验证，用户 $\small 1$ 按比例得到的 $\small token_1$ 金额为：

$$ 
  \small \begin{aligned} \frac{L_{1}}{L_{1} + L_{d}} * (R + C_{a}) = \frac{L_{1}}{L_{1} + L_{d}} * R + r * \frac{L_{d}}{L_{1} + L_{d}} * R \end{aligned} \tag{3.3.3}
$$

上式第一项正是在不考虑补偿时，用户 $\small 1$ 应得到的 $\small token_1$ 交易收入，第二项是获得的交易补偿费，即 $\small (3.3.1)$ 中的 $\small C^{'}_a$。

用户 $\small 2$ 按比例得到的 $\small token_1$ 金额为：

$$ 
  \small \begin{aligned} \frac{L_{d}}{L_{1} + L_{d}} * R - r * \frac{L_{d}}{L_{1} + L_{d}} * R \end{aligned} \tag{3.3.4}
$$

上式第二项正是用户 $\small 2$ 支付的内部交易补偿费。Unibuy 协议实现中，实际记录并处理的补偿金额是 $\small C_{a}$，而不是 $\small C^{'}_{a}$。内部交易补偿费率一般设置为 $\small 0.2\%$。

### 3.4 内部交易价差补偿费

如上所述，如果新订单的价格区间跟已经部分成交的价格区间重叠，需要通过补偿机制，避免不合理的套利机会。新旧流动性聚合时，隐含的内部交换以 $\small token_1$ 计算，数量为 $\small (3.2.1)$ 中的 $\small R_x$。Unibuy 协议规定，该内部交易以交易对的当前价格 $\small P_0$ 计价。($\small P_0$ 为挂单成交后的 $\small P_0$，其值为挂单价格区间的低端价格，与挂单时交易对的当前价格，二者之中的最低价格)。虽然 $\small R_x$ 的平均交易价格为 $\small \sqrt{P_a * P_x}$，$\small P_x$ 是流动性再平衡时交易对当时的价格 $\small P_0$，$\small P_a$ 是 (3.1) 中所所说的 $\small P_r$，但因为 $\small P_x$ 是不确定的，Unibuy 取价格范围 $\small (P_a, P_b)$ 的高端价格 $\small P_b$ 计算 $\small R_x$ 的名义价值，由于 $\small P_0$ 与 $\small \sqrt{P_a *P_b}$ 之间的价差产生的套利空间，用户 $\small 2$ 需要以内部交易价差补偿费的形式，补偿给先期加入流动性的用户。假设该补偿费用 $\small C_b$ 表示，$\small C_b$ 应满足下面的公式：

$$ 
  \small \begin{aligned} \frac{P_0}{\sqrt{P_a* P_b}} = \frac{\cfrac{L_d}{L_1 + L_d} *(R+C_b) - C_b}{\cfrac{L_d}{L_1 + L_d} * R}  \end{aligned} \tag{3.4.1}
$$

上式的基本逻辑是加入价差补偿处理后，用户 $\small 2$ 的 $\small token_1$ 实际所得与名义所得的比例应满足 $\small P_0 / \sqrt{P_a * P_b}$ 的比例关系，上式简化后得到 $\small C_b$ 为:

$$
  \small \begin{aligned} C_b = (1 - \frac{P_0}{\sqrt{P_a* P_b}}) * {\cfrac{L_d}{L_1} * R}  \end{aligned} \tag{3.4.2}
$$

现在进一步考虑：如果该部分成交的流动性区间此前已经收到了一部分补偿，那么内部交易价差补偿费应如何计算？其时流动性状态可用下表表示：

$$ 
  \small \newcommand{\arraystretch}{1.8} \begin{array}  {| c ||  c | c | c |  c |}
  \hline
  \text{区间流动性状态} &\text{总流动性}  &\text{净流动性}     &token_1\ \text{数量} &\text{补偿金额} \\
  \hline
  \text{加入新流动性前}  &{L_1}        &L_2          &R  & O \\
  \hline
  \text{加入新流动性后}  &{L_1 + L_d}  &{L_2 + L_d}  &R & O + C_c \\
  \hline  
  \text{撤回新流动性后}  &{L_1}    &{\dfrac{L_1}{L_1 + L_d} * (L_2 + L_d)}  &{\dfrac{L_1}{L_1 + L_d}} * R & {\dfrac{L_1}{L_1 + L_d}} * (O + C_c) \\[0.15cm]
  \hline  
 \end{array}
$$

如上表所示，流动性区间此前已经收到的补偿金额记为 $\small O$。按照与公式 $\small (3.4.1)$ 类似的推导逻辑，可得：

$$
  \small \begin{aligned} \frac{P_0}{\sqrt{P_a* P_b}} = \frac{\cfrac{L_d}{L_1 + L_d} *(R + O + C_c) - C_c}{\cfrac{L_d}{L_1 + L_d} * R}  \end{aligned} \tag{3.4.3}
$$

因此有：

$$
  \small \begin{aligned} C_c = (1 - \frac{P_0}{\sqrt{P_a* P_b}}) * {\cfrac{L_d}{L_1} * R} + {\cfrac{L_d}{L_1} * O}  \end{aligned} \tag{3.4.4}
$$

显然，当 $\small O = 0$ 时，$\small C_c$ 退化为 $\small C_b$。

进一步可得：

$$
  \small \begin{aligned} {\dfrac{L_1}{L_1 + L_d}} * (O + C_c) =  O + (1 - \frac{P_0}{\sqrt{P_a* P_b}}) * {\cfrac{L_d}{L_1 + L_d} * R}  \end{aligned} \tag{3.4.5}
$$

公式 $\small (3.4.5)$ 左侧的第二项，就是新增流动性为该价格区间带来的新增补偿。

  ### 3.5 合计内部交易补偿费

$\small C_a$ 与 $\small C_c$ 合在一起，就是用户 $\small 2$ 需要支付的总补偿费用，用 $\small C$ 表示为：

$$ 
  \small \begin{aligned} C = (1 - \frac{P_0}{\sqrt{P_a* P_b}} + r) * {\cfrac{L_d}{L_1} * R} + {\cfrac{L_d}{L_1} * O}  \end{aligned} \tag{3.5}
$$

这里的补偿金额 $\small C$ 并不是挂单所有者需要额外转入的字面金额，而是协议算法用于在相关订单之间正确分配已收到 $\small token_1$ 的一个参数。无论从仿真结果还是理论分析看，公式 $\small (3.5)$ 都能够满足这一分配要求。

用户挂单时，其价格区间可能会与多个部分成交的流动性区间重叠并聚合。Unibuy 协议会计算该挂单在所有聚合价格区间上的补偿金额，并将累积补偿额记录在挂单信息中。当用户关闭或清算该挂单时，协议会先按该用户的流动性占比计算其应得的 $\small token_1$ 名义总额，再从中扣除总补偿金额，得到用户最终收到的 $\small token_1$ 数量。

一个价格区间可能会多次加入新的挂单，并按上述规则重复计算补偿金额。每个 $\small tick$ 的 $\small tickInfo$ 都会记录该区间累计收到的 $\small token_1$ 交易收入，以及累计补偿金额。当用户关闭挂单时，协议会将累计 $\small token_1$ 收入与累计补偿一并纳入结算，再根据用户的流动性占比计算其实际收到的 $\small token_1$ 数量。

虽然在用户关闭挂单时，内部交易补偿会参与收益计算，但它本质上是零和的，即所有价格区间中补偿收益的总和，必然等于所有用户订单信息中作为扣减项记录的补偿金额总和，二者相互抵消。内部交易补偿只是协议内部的记账与价值平衡机制，不会对无关的流动性区间产生影响，对外部吃单交易也完全透明，只会在用户挂单或关闭挂单时触发相应处理。

### 3.6 流动性区间拆分

用户挂单时，如果给定价格区间 $\small (P_l, P_u)$ 的价格边界 $\small P_l$ 和/或 $\small P_u$ 处于某个流动性区间 $\small (P_a, P_b)$ 的中间，并且该流动性区间是部分成交的，此时需要对该流动性区间进行拆分处理，即将流动性区间拆成上下两个流动性区间 $\small (P_a, P_s)$ 和 $\small (P_s, P_b)$，其中 $\small P_s$ 为 $\small P_u$ 和/或 $\small P_l$。流动性区间拆分的目的是为了进行流动性聚合，流动性区间拆分会将部分成交接收到的数量为 $\small R$ 的 $\small token_1$ 按照下面的公式拆成上下两个部分 $\small R_u, R_l$：

$$
  \begin{aligned} \small 
  R_u \ = \ &\frac{\sqrt{P_b} - \sqrt{P_s}}{\sqrt{P_b} - \sqrt{P_a}} * R \\[3mm]
  R_l \ = \ &R - R_u \\[3mm]
  \end{aligned} \tag{3.6}
$$

如果该流动性区间存在内部交易补偿费用，也要按照上面的规则进行拆分。

## 4 技术实现

下面介绍 Unibuy 协议在合约实现层面的关键技术点。

### 4.1 全局状态

Unibuy 智能合约内，每个交易对包含下表所示的全局状态：

$$ 
  \small \newcommand{\arraystretch}{1.8} \begin{array}  {| c ||  c | c |}
  \hline
   \hspace{0.6cm} \text{类型} \hspace{0.6cm} & \hspace{1cm} \text{变量名称} \hspace{1cm}  &\hspace{0.6cm} \text{标识} \hspace{0.6cm}   \\
  \hline
  uint160  &{sqrtPriceX96}        &{\sqrt{P_0}}           \\
  \hline
  uint24  &{tick}  &{I_t}  \\
  \hline
  uint32  &{poolHeight}        &{H_g}           \\
  \hline
  uint8  &{takerFee}  &{F_t}  \\
  \hline
  uint8  &{offsetFee}  &{F_o}  \\
  \hline  
  uint8  &{dayNum}  &{D_n}  \\
  \hline
  uint8  &{tickGapLimit}  &{G_t}  \\
  \hline
  uint8  &{bottomDepth}  &{B_d}  \\
  \hline  
 \end{array}
$$

$\small P_0$ 是交易对当前的价格，$\small I_t$ 是与该价格对应的 $\small tick$ 值。

交易对会维护一个全局高度参数 $\small H_g$，初始值 从 1 开始，每当交易对价格上涨，跨越上方 $\small tick$ 时，$\small H_g$ 便加 1。当用户挂单时，用户的挂单信息中，会记录挂单当时 $\small H_g$ 的值。在用户关闭挂单时，需要参考该值，与撤单当时的高度值 $\small H_g$，判断挂单的成交状态，计算用户挂单的成交收益。

$\small F_t$ 是吃单交易的费率，缺省值是 30 个基点，对应 0.3% 的交易手续费，以 $\small token_1$ 计费。

$\small F_o$ 是挂单触发内部交易的交易补偿费率，也是以 $\small token_1$ 计费。

$\small D_n$ 表示一个内部的日期索引，用于判断已完全成交的挂单是否在规定期限内关闭。

$\small G_t$ 是挂单价格区间 $\small (P_l, P_u)$ 的最大间隔。由于挂单可能触发再平衡、区间拆分和补偿处理，价格跨度越大，链上执行工作量通常也越大。如果用户希望覆盖更宽的整体价格区间，可以拆分成多个挂单。

$\small B_d$ 用于存储当前活跃区间下边界相对于当前 tick 的偏移量。

### 4.2 Tick 状态

合约内部存储一个 $tick$ 索引到 $\small tickInfo$ 结构的映射，$\small tickInfo$ 包括如下字段：

$$ 
  \small \newcommand{\arraystretch}{1.8} \begin{array}  {| c ||  c | c |}
  \hline
  \hspace{0.6cm} \text{类型} \hspace{0.6cm} & \hspace{1cm} \text{变量名称} \hspace{1cm}  &\hspace{0.6cm} \text{标识} \hspace{0.6cm}   \\
  \hline
  uint128  &{liquidityGross}        &{L_g}           \\
  \hline 
  int128   &{liquidityNet}           &{L_n}           \\
  \hline
  uint96  &{amountReceived}         &{R_r}            \\
  \hline
  uint96  &{amountOffset}           &{R_o}            \\
  \hline  
  uint32  &{tickHeight}             &{{H_t}}    \\
  \hline  
  uint32  &{activeEntryCount}       &{A_c}     \\
  \hline  
  bytes32[]  &{clearanceList}       &{C_t}     \\
  \hline  
 \end{array}
$$

$\small tickInfo$ 可能会有两个不同的状态，一是其中的流动性完全没有成交，一是其中的流动性已经部分成交。

当流动性完全没有成交时，$\small L_g$ 表示所有以该 $\small tick$ 为价格边界的挂单的总流动性。$\small L_n$ 表示所有以该 $\small tick$ 为价格边界的挂单的净流动性，即穿越该 $\small tick$ 时流动性的变化量。此时 $\small R_r, R_o$ 没有意义，其值为 0.

当流动性部分成交时，$\small L_g$ 表示该 $\small tick$ 上方价格区间的总的流动性，$\small L_n$ 表示该价格区间经过流动性再平衡后的剩余净流动性。

$\small R_r$ 表示流动性部分成交后收到的 $\small token_1$ 的数量，$\small R_o$ 表示所有后发挂单的内部交易手续费与前向价差补偿费的总和。

$\small H_t$ 是与该 $\small tick$ 相关的所有流动性挂单的最低 $\small poolHeight$。

当价格上穿价格区间时，下端 $\small tick$ 中的 $\small L_g, L_n, R_r, R_o, H_t$ 都会被清零。上端 $\small tick$ 中的 $\small L_g$, $\small L_n$, $\small R_r$, $\small R_o$, $\small H_t$ 会被更新。

$\small C_t$ 是该 $\small tick$ 的可索引清算历史。$\small A_c$ 表示该 $\small tick$ 上仍然活跃的的清算记录条数，即使某个 $\small tick$ 的其他成交状态已经清空，只要仍有活跃的历史清算记录，该 $\small tick$ 仍然会处于激活状态。

### 4.3 清算列表

合约会为每个被价格向上穿越的 $\small tick$ 维护一份清算列表，用于在关闭对应挂单时计算用户的挂单收益。

$$ 
  \small \newcommand{\arraystretch}{1.8} \begin{array}  {| c ||  c | c |}
  \hline
  \hspace{0.6cm} \text{类型} \hspace{0.6cm} & \hspace{1cm} \text{变量名称} \hspace{1cm}  &\hspace{0.6cm} \text{标识} \hspace{0.6cm}   \\
  \hline
  uint128  &{liquiditySold}        &{L_s}           \\
  \hline
  uint96  &{amountReceived}        &{R_r}           \\
  \hline
  uint8  &{gap}  &{G_x}  \\
  \hline  
  uint24  &{crossHeight}  &{X_h}  \\
  \hline  
 \end{array}
$$

$\small L_s$ 是价格向上穿越该 $\small tick$ 时，当前价格区间内被卖出的总流动性。

$\small R_r$ 是出售总流动性收到的总的 $\small token_1$ 的数量。用户挂单按照挂单的流动性按比例分享 $\small R_r$。$\small R_r$ 的值，是直接出售 $\small token_0$ 收到的 $\small token_1$ 数量，与收到的所有内部交易补偿收益的总和。

$\small G_x$ 表示该次跨越的价格区间宽度。

$\small X_h$ 存储价格上穿时 $\small poolHeight$ 的低 24 位。

### 4.4 挂单信息

  用户的挂单包括如下信息：

  $$ 
    \small \newcommand{\arraystretch}{1.8} \begin{array}  {| c ||  c | c |}
    \hline
  \hspace{0.6cm} \text{类型} \hspace{0.6cm} & \hspace{1cm} \text{变量名称} \hspace{1cm}  &\hspace{0.6cm} \text{标识} \hspace{0.6cm}   \\
    \hline
    uint128  &{liquidity}        &{L_p}           \\
    \hline
    uint32  &{orderHeight}         &{H_p}  \\
    \hline
    uint96  &{amountDeduction}    &{D_p}           \\
    \hline
  \end{array}
$$

$\small L_p$ 是挂单的流动性。$\small H_p$ 是挂单时交易对的当前高度值。$\small D_p$ 是该挂单的总补偿金额，包括内部交易补偿费和价差补偿费。该金额不是用户挂单时实际需要支付的金额，而是一个虚拟金额，用于准确计算用户挂单的成交收益，同时阻止不合理的挂单套利。当挂单被关闭时，该金额会从用户收到的 $\small token_1$ 中扣除。

挂单的价格范围以及交易对索引信息都编码在挂单记录的映射键中，交易对合约本身无须显式存储这些信息，但 Unibuy 路由合约需要保存和管理这些信息。

## 5. 订单

用户下单时，需要指定待交易的两个资产 $\small token_0$ 和 $\small token_1$，以及买入或卖出的价格与数量。Unibuy 合约会根据这两个 Token 以及用户的交易意图，自动映射到对应的单向交易对，并判断价格条件是否允许按吃单处理。如果价格条件满足，就按吃单立即成交；否则按挂单处理。如果只能部分成交，则先将可成交部分作为吃单执行，剩余部分可以取消，也可以转为挂单。

### 5.1 挂单

挂单是用户的订单没法立即成交，合约需要将订单流动性与交易对已有的流动性进行聚合，等待后续吃单成交。挂单交易有可能会触发区间流动性的内部交易，以及前向补偿处理，导致挂单用户需要以 $\small token_1$ 形式支付一定数量的补偿。该补偿不需要用户立即支付，而是在后面挂单成交后从成交收入中扣除。一般情况下，即使用户挂单完全没有成交，内部交易的收益也是可以覆盖该补偿的。该补偿不是挂单用户的损失，而是避免内部交易套利的一种合理的价值平衡。

挂单给出的价格范围，不得高于镜像交易对的价格，高出部分是可以立即成交的，合约会进行相应检查。

### 5.2 关闭挂单

用户可以在挂单未成交、部分成交或完全成交的任何状态下关闭自己的挂单。

即使用户的挂单从未成交，关闭挂单时收到的 $\small token_0$ 数量也不一定等于最初挂单时支付的数量。如果该挂单触发过内部交易机制和前向补偿机制，用户可能会收到数量减少的 $\small token_0$，以及一定数量的 $\small token_1$。

如果用户的挂单已经完全成交，用户应在一周内及时关闭挂单。若在一周内关闭挂单，则不收取任何费用。超过一周后，UniBuy协议会收取一定的延迟关闭费用，以 $\small token_1$ 支付；同时，协议会允许第三方代替用户关闭订单，此时用户可能需要支付一定的关闭服务费，费率通常为所收取 $\small token_1$ 的 $\small 0.1\%$。Unibuy 协议项目方也可以提供这项服务。该机制可以避免大量已完全成交的挂单长期堆积在合约中，从而影响创建挂单和关闭挂单的性能。

### 5.3 吃单

当用户订单允许部分或全部成交时，订单会按照吃单处理。吃单需要支付交易手续费，费率一般是 $\small 0.3\%$，以 $\small token_1$ 支付。

吃单会立即成交。如果用户订单不是可以全部立即成交的吃单，用户也可以指定下面几种处理方式：
  1. 部分成交，其余撤销；
	2. 部分成交，其余挂单；
  3. 不成交，全部撤销；

### 5.4 转单

转单是用户在挂单的同时，可以指定如果挂单全部成交，成交后收到的 $\small token_1$ 可以当做镜像交易对的 $\small token_0$ 在指定的价格范围内再次挂单。

转单不会自动执行，需要由用户、第三方服务商或 Unibuy 协议项目方触发。如果不是由用户本人触发，则用户可能需要支付一定的费用。

## 6. 总结

Unibuy 协议是恒定乘积自动做市商类型 DEX 协议的一次重大演进，可以解决现有 DEX 存在的三明治攻击、无偿损失等问题。传统的做市商依然可以在协议中通过挂单、吃单进行做市，但其交易行为在协议层面与普通交易用户是一样的，协议也不再需要将交易费用收入让渡给做市商。这使得协议项目方能够从交易手续费用中获得应有的收益，以支撑项目的持续稳定发展。普通用户也可以将闲置资产挂单销售，成交后利用转单的方式自动完成高抛低吸，实现市场波动的套利。如果大量个人用户参与该套利，则可以一定程度上抑制市场波动，也为普通用户带来被动收益。

Unibuy 协议可以提供与中心化交易所类似的订单簿体验，但不再需要将用户资产托管到中心化交易所，导致中心化风险。由于区块链交易的时延特性以及不连续性，用户挂单时，应该是审慎认真的，是用户意愿的真实体现。用户挂单在链上都是真实可见的，可以避免 CEX 中一些用户反复挂单撤单、自卖自卖、操纵价格、误导交易用户的问题。

DEX 协议需要持续演进和发展，Unibuy 协议是 DEX 协议具有一定突破意义的探索和进步，相信将来还会有更多更好的关于 DEX 协议的创新。
